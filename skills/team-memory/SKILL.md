# team-memory

repo のルート直下の `.memory/` に、作業から得た知見を Markdown で残す。記憶は PR に含めてレビューを通し、チーム全員のエージェント（Claude Code・Codex）が読む。個人用の記憶（Claude Code の auto memory など）とは同期しない。チームで使う価値のある知見だけをここに書く。

`.memory/` は作業対象の repo のルートを基準に探す。worktree では、その worktree の中の `.memory/` を読み書きする。

## 読む

過去の判断や試した方法が関係しそうな作業では、着手前に `.memory/INDEX.md` を見る。

- 開くのは、今の作業に関係する行のファイルだけ。全部は読まない。関係する行がなければ、普段は INDEX だけで終える。
- INDEX.md が分野の一覧になっているときは、関係する分野の `INDEX.md` だけを開く。
- 以前の経緯や、過去に試したかどうかを確かめる必要がある作業（ユーザーに聞かれたときなど）では、INDEX で見つからなくても `grep -ril <キーワード> .memory/` で探す。`archive/` も対象に含める。
- 同じ会話の中で、一度読んだ記憶を読み直さない。
- 誤字・書式の修正、依存の更新など、過去の判断と関係のない作業では読まない。

読んだ記憶は次のように扱う。

- 記憶は書いた時点の事実。使う前に、適用範囲（入力の条件、対象のバージョンやコード）が今と合っているか確かめる。
- 記憶と今のコードが食い違うときはコードを正とし、そのことをユーザーに伝える。
- `status: superseded` の記憶は、本文の先頭にある統合先の記憶を読む。
- ユーザーの案が、不採用の記憶と同じ方法なら、着手する前にその記憶を示す。再検討の条件を満たしているなら、そう伝えたうえで進めてよい。

## 書く

### 書くかどうか

「次の担当者の判断や、やり直しの手間を変えるか」で決める。新しい知見がなければ書かない。

- 書く: 方針の決定と理由、試して捨てた方法と理由、計測値、前提が変わったこと。PM が決めた優先順位や前提、見送った案も含む。
- 書かない: 変更の一覧、コマンドの出力、作業の時系列、通常のテストの成功、README・仕様書・Issue に十分書いてあること（リンクで済ませる）。

書くタイミングは、方針を決めたとき、実験を打ち切ったとき、PR を作る前、ユーザーに頼まれたとき。PR にならずに捨てた試行も、残す価値があれば記憶だけの変更として PR にする。

### 新しく書くか、更新するか

同じテーマ（同じ対象についての判断）は、1つのファイルで育てる。既存のファイルを直したら、`updated` をその日にする。

- 同じ結論を補強する追加の検証は、`根拠` に追記する。
- 方針が変わったとき（以前の結論を覆したとき）は、次の4つを同じ PR で行う。
  1. そのファイルの `結論` を今の方針に書き換え、`title` と INDEX の行も合わせて直す。ファイル名は変えない。
  2. `経緯` に「YYYY-MM-DD: 以前は〜としていたが、〜のため〜に変えた」を1行足す。以前の結論と、変えた理由が分かるように書く。
  3. 方針転換が README・仕様書・設計文書など repo の文書に関わるなら、その文書も直す。
  4. 関係するほかの記憶の `結論` が今の方針と食い違うなら、それも直す。
- 別のファイルに統合したとき（同じテーマの重複をまとめたときを含む）だけ、元のファイルを `status: superseded` にし、本文の先頭に統合先へのリンクを1行足して、`archive/` に移す。統合先の `経緯` には、統合したことを1行書く。
- 矛盾する `current` の記憶を並べない。条件の違いで両立するなら、それぞれの適用範囲に条件を書く。

### ファイル

ファイル名は `YYYY-MM-DD-<内容が分かる英小文字の短い名前>.md`。日付は初めて書いた日。作った後は改名しない（分野のフォルダや `archive/` への移動はしてよい）。

```markdown
---
title: 固定しきい値の二値化は採用しない
author: <GitHub login>
date: 2026-10-20
status: current
agent: claude-code
related:
  - "#12 丸記号の検出精度の改善"
---

## 結論
スキャン画像の二値化には適応的しきい値（blockSize 31, C 5）を使う。固定しきい値は採用しない。
適用範囲: 現在受け付けているスキャン画像。写真入力は未評価。

## 根拠
- 固定しきい値（128）では、薄い図面で丸が欠け、濃い図面で文字を丸と誤検出した。
- 再現率: 固定 0.62、適応的 0.81（評価用30枚、2026-10-20 計測、確定）。速度差は1枚あたり 4ms。

## 経緯
- 2026-10-20: 初めて記録。

## 再検討の条件
入力の濃さがそろう前処理が入った場合。

## 内部メモ
（先方に出さない内部の呼び名・経緯。なければ見出しごと省く）
```

frontmatter:

| 項目 | 必須 | 書き方 |
|---|---|---|
| `title` | 必須 | 対象と結論が分かる文。INDEX の1行になる |
| `author` | 必須 | 作業を指示した人の GitHub login。その repo のコミットと同じアカウントにするため、まず `git config user.email` が `<数字>+<login>@users.noreply.github.com` の形ならその login を使う。そうでなければ `gh config get -h github.com user`（ネットワーク不要）、だめなら `gh api user -q .login`。どれでも取れなければユーザーに聞く。推測しない |
| `date` | 必須 | 初めて書いた日 |
| `status` | 必須 | `current` か `superseded`。不採用という結論も、今有効なら `current` |
| `agent` | 任意 | 書いたエージェント（`claude-code`、`codex` など） |
| `updated` | 任意 | 既存のファイルを直した日。直したときだけ書く |
| `related` | 任意 | 関係する Issue・PR を「番号 タイトル」で |

本文:

- 見出しは `結論`・`根拠`・`経緯`・`再検討の条件`・`内部メモ`。`結論` 以外は、該当がなければ見出しごと省く。
- `経緯` には、方針が変わった日と以前の結論・変えた理由、ほかの記憶を統合したことだけを書く。作業の時系列は書かない。
- `結論` は、社外の人が読んでも通じる言葉で書く。内部の呼び名、他の案件の話、資料に出さない経緯は `内部メモ` にだけ書く。
- 数値には、評価に使ったデータ・件数・計測日と、確定か暫定かを書く。分からないものは「計測日は未確認」のように、分からないと書く。
- 観測したこと、推測、決めたことを区別して書く。原因が切り分けられていなければ、そう書く。
- 人名は本文に書かない。人を示すのは `author` だけにする。
- Issue・PR の番号は `related` に置き、本文では内容で言う。
- 遅れは「遅れた」と書かず、原因と見込みの日付で書く。
- 本文は短くする。目安は画面1枚。

### INDEX.md

`current` の記憶だけを、1件1行で載せる。リンク文は `title` と同じにし、結論が分かるようにする。

```markdown
# チームの記憶

- [固定しきい値の二値化は採用しない](2026-10-20-fixed-threshold-rejected.md)
```

- 新しい行はファイル名の順の位置に足す。他の行の並べ替えや整形はしない。
- `superseded` にした記憶や `archive/` に移した記憶の行は、INDEX から消す。
- `.memory/` がなければ、最初の記憶を書くときに、見出し `# チームの記憶` だけの INDEX.md を作る。
- マージで INDEX.md が衝突したら、両側で足した行を両方残す。そのうえで、`superseded` になった記憶の行は消す。

### 記憶が増えたとき

膨大になっても探せることを優先する。定期的な整理はしない。

- **分野に分ける**: 記憶を書いて INDEX.md に載る記憶が100件を超えたら、その場で記憶を分野ごとのフォルダ（例: `.memory/detection/`）に移し、フォルダごとに `INDEX.md` を作る。後回しにしない。上の INDEX.md は、分野の一覧（1分野1行。リンクと、その分野に入っている記憶の要約）にする。分野のフォルダの INDEX も100件を超えたら、同じように分ける。
- **archive に移す**: 統合して `superseded` にした記憶や、対象のコード・機能がなくなった記憶は、`.memory/archive/` に移して INDEX から消す。archive は普段は読まず、grep で探すときだけ対象にする。
- **整理する**: 頼まれたときだけ行う。同じテーマの記憶を1つにまとめ、まとめた先の `経緯` に統合したことを書き、元のファイルは `superseded` にして archive に移す。
- 分野に分ける作業と整理は、コードの変更とは別のコミットにする。整理は記憶だけの PR にする。

## 報告資料の材料にする

定例資料などを作るために記憶を集めるとき:

1. 期間と課題で絞る。期間は `date`・`updated` に加えて `経緯` の各行の日付で見る（`updated` は最後に直した日なので、途中の変更を取りこぼさないため）。課題は `related` で見る。期間中に方針が変わった記憶は、`経緯` から変更点と理由を拾う。
2. 資料には `結論` と `根拠` を使う。`内部メモ` は理解の助けにだけ使い、写さない。
3. `author` と Issue・PR の番号は、社外向けの資料に出さない。暫定の数値を使うときは、暫定と明記する。
4. 記憶に書いていないことを補って断定しない。分からない点は、資料を作る人に確認を求める。
